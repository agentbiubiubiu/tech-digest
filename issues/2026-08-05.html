第 72 期：Agent 日志不能只记答案，还要记清它调用过什么

第 72 期 · 2026年8月5日，星期三

LLM 0.32 的功能与日志设计由项目作者和官方文档确认；本期没有把作者的发布判断当作性能 Benchmark。

🎯 本期核心判断：AI CLI 正在从模型外壳变成可审计运行时；推理、工具调用、结果和内容应该作为有类型事件持久化，才能复现失败、计算成本和安全边界。

🔥 主故事

一条 Agent 日志里，为什么不能只剩最后的回答

你把 `llm` 的输出管道给另一个命令，结果推理过程、工具消息和最终答案全挤在一起。人能勉强看懂，脚本却不知道哪一段才是稳定输出。

Simon Willison 在 8 月 4 日发布 LLM 0.32 正式版。项目此前的 rc2 已在第 70 期出现，本次新增事实是正式发布及完整设计说明：推理轨迹默认进入 stderr，stdout 保持可组合；工具调用和结果以有类型事件流输出；SQLite 日志改成内容寻址的消息存储。

核心冲突Agent 越透明，日志就越多；但如果把推理、工具参数、结果和最终文本压成一段字符串，管道会被污染，审计也无法判断一条内容是模型生成、工具返回还是人工批准。
转折点真正的转折不是又多支持了几个模型，而是把一次调用拆成可识别的事件。模型响应、推理片段、工具调用、工具结果和附件各有类型，日志才能被重放、查询和计费。
为什么是现在Coding Agent 已经会访问网页、执行代码、调用 MCP 和跨多个提供商运行。平面文本只能告诉你最后说了什么，不能回答它访问了哪里、写了什么、哪一步失败以及费用来自哪次调用。
对团队的启发选一条真实 Agent 任务，把当前日志改写成 typed events；验证能否从日志重建工具顺序、失败点、人工审批、Token 和文件变更，同时对敏感内容设置脱敏与保留期限。

2026-08-04 发布 0.32 正式版推理轨迹默认输出到 stderr，最终结果保留在 stdoutOpenAI 与 Anthropic 的服务端工具被统一为工具事件SQLite 消息存储采用内容寻址，重复内容只保存一次

我的判断：我更关注这套事件模型，而不是支持模型数量。团队需要的不是保存更多自然语言，而是统一 response ID、模型参数、工具输入输出、内容哈希、审批和错误状态；推理轨迹只能作为调试信号，不能被当成事实或完整内部思维证明。

Agent 的最后一句话是结果，不是执行记录。

来源：simonwillison.net

🧩 本期概念库

1. 有类型事件日志（Typed Event Log）

一句话解释：把模型文本、推理片段、工具调用、工具结果、附件和错误保存成不同事件，而不是拼成一段字符串。

为什么重要：只有结构化事件才能稳定重放、检索、计费和审计。

团队应用：为每个 Agent run 记录 response ID、事件类型、时间、来源、审批和错误状态。

2. 内容寻址消息存储（Content-addressed Message Store）

一句话解释：以内容哈希保存消息块，重复内容只存一次，引用关系留在会话记录中。

为什么重要：长上下文与重复工具结果会快速放大日志体积和一致性问题。

团队应用：对大段输入、附件和工具结果计算哈希，并保留脱敏、生命周期与删除映射。

3. 宽松评测环境（Permissive Evaluation Environment）

一句话解释：为了测试模型上限而主动关闭部分安全层、开放互联网或增加工具权限的实验配置。

为什么重要：没有逃逸并不等于没有外部风险，实验本身已经连接真实世界。

团队应用：使用目标白名单、外发审批、蜜罐账号、速率限制、实时监控和紧急停止。

4. 熵源失效路径（Entropy Failure Path）

一句话解释：硬件随机数不可用时，系统如何回退、重新播种以及限制密钥空间。

为什么重要：密钥一旦可预测，后续离线存储和加密强度都无法补救。

团队应用：把 RNG 故障注入、回退检查和密钥迁移写入固件安全测试。
