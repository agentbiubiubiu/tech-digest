第 101 期：协议会改变 Agent 的做事方式

第 101 期 · 2026年9月17日，星期四

同一批样本换一种输出格式，模型行为也会变；Agent 迁移要验收行为分布、客户端处理和真实任务，不能只看离线均分。

✨ 本期亮点：同一数据换成 diff patch 后，编辑行为也会变化；离线相当不等于线上等价 · 5项工具：OpenSpec、模型时效表、Claude MCP 等待边界，以及2项已有 Skill · Copilot 运行时80万行 Rust 迁移的可迁移价值在128个增量 PR，不在规模本身 · Apple、GitHub、Cloudflare 与浏览器 AI 更新均标明适用地区、权限和发布阶段

VS Code 官方技术文章配图，关联模型输出格式与行内编辑行为；不是用户项目效果截图。

🔥 主故事

同一批训练样本，为什么会教出不同的编辑习惯？

数据样本没有换，只把输出改成 diff patch，模型就更倾向局部、小步地修改代码。

VS Code 团队在9月16日的技术文章中复盘 GitHub Copilot 新一代行内建议模型：他们尝试把代码补全、下一处编辑和长距离编辑从不同路径合并到一个模型。

核心冲突使用相同样本训练的新格式模型，在离线基准上可以接近原有下一处编辑模型，但学到的仍主要是下一处编辑分布，几乎没有长距离编辑；格式变化还带来了更渐进的修改行为。
转折点团队没有把离线相当视为完成，而是通过线上试飞发现客户端还要重新处理缓存和错误，并把小型启发式基准与更大规模的人类评估结合。模型、输出协议和客户端共同决定体验。
为什么是现在这给日常 Agent 工程一个直接提醒：替换模型、工具协议或补丁格式时，即使输入样本和平均分不变，改动形状、失败方式和客户端行为仍可能发生漂移。
对团队的启发选一组脱敏、可重放的小任务，同时记录验收是否通过、改动文件与行数、重试或错误路径；固定客户端版本和输出协议后再比较模型。

我的判断：评估 Agent 迁移时应保留三层证据——任务结果、改动分布、客户端运行边界。只比较“通过了多少题”，不足以说明它会不会把一次小修扩成大段重写，也不足以证明超时、缓存和错误恢复仍然正确。

协议不是包装，它会反过来塑造模型做事的形状。

🛠️ 工具推荐

实践精选条件适用

今日实用工具：OpenSpec，先把需求变化留在规格里

OpenSpec 用可维护的规格连接需求、Agent 与实现校验。对跨端需求，它的新增价值不是再写一份长文档，而是让“要做什么、后来改了什么、实现是否匹配”有同一入口。近期由 HN 发现，首发日期未核验，不写成今日发布。

适合你的环节：减少 Web、iOS、Android 和后台对同一需求各自解释一次的偏差。

今天怎么试：挑一个不含业务秘密的小需求，只写目标、非目标、三个验收例子；先与现有需求文档比较是否减少歧义，再决定是否接入仓库。

边界：尚未安装或接入。公开站点的使用量与星标是项目自述，本期不作为效果证据；规格不会自动证明代码正确，也不能替代真实接口与设备验收。

实践精选方法可试

模型时效表：在回答“当前版本”前先查日期

How Stale Is Your AI? 把模型发布日期与厂商公开的训练截止日期分开，并提供带来源的 models.json。它更适合作为核验入口和提示规则，不应把训练截止日期误写成联网能力或完整知识边界。

适合你的环节：减少 Agent 凭旧记忆回答当前模型、版本与日期的问题。

今天怎么试：遇到模型选型或版本问题时，先读取 models.json 的日期和来源，再回到厂商官方页面确认；只验证一项，不把整张表复制进上下文。

边界：10/20 个模型有公开截止日期，缺失表示站点未找到证据，不代表厂商从未披露。第三方整理可能滞后，不能替代最终官方核验。

实践精选条件适用

Claude Code 2.1.274：给首轮 MCP 连接设等待边界

新版本加入 CLAUDE_CODE_MCP_STARTUP_WAIT_MS，用于限制非交互任务首轮等待 MCP 服务器的时长；还修复长时间工具调用超时、权限错误误报登录过期和损坏会话反复重试等问题。

适合你的环节：区分自动化是真的卡死，还是首轮等待某个 MCP；让失败更快暴露。

今天怎么试：如果实际使用该版本，先在隔离的非交互任务中记录一个正常 MCP 和一个不可达 MCP 的启动时间；设置上限后确认正常服务仍能连接，失败信息仍保留服务名和权限原因。

边界：未核验本机是否安装该版本。0 表示不等待，可能让本可恢复的服务直接缺席；只缩短等待不解决服务故障，环境变量变更也不能全局盲配。

实践精选已有能力可用

tdd Skill：先把失败例子固定下来

已有 TDD Skill 适合业务规则、小型修复和边界条件：先写一个能稳定失败的例子，再让最小实现通过，最后整理结构。今天没有新发布，它是现成能力。

适合你的环节：减少 Agent 在没有可判定反馈时同时改代码、猜需求和扩大范围。

今天怎么试：直接说：“用 tdd 修这个脱敏规则，先给我看失败用例和验收边界；只改相关文件。”对纯视觉微调或高成本端到端环境，先判断测试是否值得。

边界：测试要验证行为，不能照抄实现；旧代码难以隔离时，先建立最小可观察点。真机、线上、权限和生产数据仍需单独验收。

实践精选已有能力可用

research Skill：把结论和一手来源放进仓库

已有 Research Skill 面向需要一手资料和可追溯结论的技术问题。它适合 SDK 迁移、标准变化和复杂选型，产出可审查的 Markdown，而不是只留聊天摘要。

适合你的环节：减少技术选型中重复搜索，以及结论离开会话后无法复核的问题。

今天怎么试：给一个窄问题、最多三个来源类型和明确截止时间，例如“核对 iOS 27.2 对订阅接入的变化，只看 Apple 官方资料，写一页结论”。

边界：不适合一句话事实或无需留档的小问题；网页内容仍是不可信输入。研究报告不能代替构建、API 调用或设备验证。

🧩 本期概念库

1. 行为分布漂移

一句话解释：总体通过率相近时，修改范围、步骤和失败方式仍可能发生系统性变化。

为什么重要：它决定审查成本和线上风险，不会被单个均分完整表达。

团队应用：比较文件数、改动行数、重试和错误路径。

2. 协议塑形

一句话解释：输出格式、工具协议和客户端处理会影响模型如何表达和执行动作。

为什么重要：协议变化可能成为行为变化，而非单纯兼容层调整。

团队应用：迁移协议时固定任务样本并复查改动形状。

3. 增量切换

一句话解释：把大型迁移拆成能独立合入、验证和回退的小批次。

为什么重要：让真实反馈在迁移完成前持续到来。

团队应用：每个切片绑定消费者、回归项和回退条件。

4. 用途分离

一句话解释：同一主体或爬虫的搜索、训练和摘要用途应分别授权。

为什么重要：身份相同不代表数据使用目的相同。

团队应用：记录策略对象、用途和实际执行证据。

主故事：离线相当，为什么线上还会变

VS Code 团队复盘 GitHub Copilot 新一代行内建议模型时，尝试把代码补全、下一处编辑和长距离编辑合成一个模型。他们用了相同数据样本，只改变输出表达，新的模型在离线基准上可以接近原有模型，但学到的主要仍是下一处编辑，长距离编辑很少。diff patch 格式还让修改更渐进。这不是一个简单的格式转换问题。团队在线上试飞后，又发现缓存和错误处理需要客户端配合修正，并把小型回归基准与更大规模的人类评估结合。对我们做 Agent 工程，迁移时至少要看三层：任务是否通过，改动分布有没有漂移，客户端的超时、缓存和恢复是否还正确。原文没有在摘录里给出完整样本量和线上收益数字，所以不能把这次经验写成普遍提升。

快讯一：规格比提示词更适合承接变化

今天最值得小范围评估的候选是 OpenSpec。它把需求、变化和实现核对放在同一份可维护规格里。对 Web、iOS、Android 和后台一起交付的需求，价值在于少解释一遍，而不是多一层文档。它还没有安装。最小验证是挑一个无敏感信息的小需求，只写目标、非目标和三个验收例子，再和现有需求文档比较歧义是否减少。公开站点的使用量和星标是项目自述，不拿来证明效果。

快讯二：给 MCP 等待设上限，也要保留故障原因

Claude Code 2.1.274 新增首轮 MCP 启动等待时间参数，也修复了长时间工具调用超时、权限不足被误报成登录过期，以及损坏会话无限重试的问题。这个变化适合自动化：不可达服务不该让任务无限等待。但等待设为零，也可能让本来能恢复的服务直接缺席。正确验证是同时准备一个正常服务和一个不可达服务，检查总耗时、服务名、权限原因和正常路径都没有退步。我们没有核验本机版本，也没有改任何环境变量。

快讯三：80万行迁移的重点不是数字

GitHub 说 Copilot 运行时从 TypeScript 重写成超过八十万行 Rust，Agent 写了大部分代码，一名主要开发者用数月完成，并通过一百二十八个 PR 逐步进入主干。所有数字和性能提升都是团队自述，不能推导别的项目也能复制。真正能借鉴的是交付方式：不要等待一次性切换，让每个切片都有真实消费者、回归反馈和回退边界。大型迁移最危险的不是代码生成不够快，而是证据来得太晚。

今天可以直接做什么

第一，遇到模型版本或训练截止日期问题，先用模型时效表找来源，再回官方页面确认。第二，需要修业务规则时，可以直接要求使用现有 tdd Skill，先展示失败例子和验收边界。第三，复杂的 SDK 或标准变化，用 research Skill 把一手来源和结论写成一页可审查文档。今天没有安装新工具、升级 IDE 或运行业务项目。若只做一个动作，我建议给下一次 Agent 模型或协议迁移补一张三列验收表：任务结果、改动形状、客户端错误路径。

今天的判断是，协议会塑造模型做事的形状。在线版保留二十条正文和五项工具，数量没有达到十项，但三项方法现在就能验证。口播是文字稿，时长为估算，没有生成或试听音频。

✅ 对团队的启发

1

下一次模型或协议迁移，增加“任务结果、改动形状、客户端错误路径”三列验收。

2

复杂业务修复优先用现有 tdd Skill 固定失败例子；纯视觉小改先判断是否值得写测试。

3

大型迁移按可独立发布与回退的切片推进，避免等到最终切换才第一次获得真实反馈。
