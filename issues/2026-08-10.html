第 77 期：一个沉默十年的 Zsh 数据丢失 Bug，靠主动崩溃才抓住

第 77 期 · 2026年8月10日，星期一

✨ 本期亮点：Zsh 的退出压缩流程曾在 SIGINT 中断读取后继续覆盖历史文件，相关 Bug 存在约十年，5.9.2 已修复 · 作者把同一故障做成 Agent Eval，约三次尝试花费超过 300 美元；结果属于单任务作者自测，不是通用 Benchmark · Claude 生成的 Dark Hours 与既有开源项目高度相似并复现旧 Bug，发布者随后关闭项目并取消 iOS 计划 · Situational Awareness 据报道向 Source Foundry 投资 4 亿美元、累计 5 亿美元；金额未获公司公告或监管文件独立确认 · T3 Code 可从 iOS、Android、Web 和桌面端控制本机编码 Agent，但新任务默认 Full access，远程接入应使用私有网络 · Gilroy 官方确认 AWS 数据中心已开工；媒体争议聚焦公众在 2024 年意见期结束后才广泛注意到项目

根据 Michael Stapelberg 的调试记录绘制：SIGINT 中断读取后，Zsh 5.9.1 仍写入不完整历史并 rename 覆盖旧文件；Zsh 5.9.2 已包含修复。

🎯 本期核心判断：面对会覆盖正确数据的异常，崩溃不是最坏结果；真正危险的是读取不完整后仍继续提交。破坏性写入前必须验证输入完整、保留旧副本，并让失败显性发生。

🔥 主故事

当读取没有完成，最安全的写入就是不要写

一个完整的历史文件先被读到一半，再被原程序认真地压缩、保存并原子替换，结果比直接崩溃更糟。

Michael Stapelberg 使用多个终端时，会让不同 Zsh 会话把命令追加到同一个 `.zsh_history`。他偶尔发现新记录整段消失，只剩很旧的历史。文件没有乱码，也没有半行文本，因此备份能恢复数据，却不能告诉他是谁在何时删掉了内容。

核心冲突Zsh 的退出流程本来想做一件可靠的事：读取完整历史、压缩到临时文件，再用 rename 原子替换旧文件。但如果 Ctrl+C 触发 SIGINT，`readhistfile` 会看到中断标记并提前停止；旧版 `savehistfile` 没有在提交前检查读取是否完整，于是把正确文件替换成了部分历史。原子替换保证了写入完整，却没有保证写入内容正确。
转折点文件监控只能看到 rename，常规 syscall 跟踪也难以保留当时的进程内状态。作者改写 Zsh：如果临时历史少于 50,000 行，就在 rename 前故意崩溃。几天后 core dump 抓到现场，回溯和中断标记终于把 SIGINT、短读与后续覆盖串在一起。
为什么是现在今天的编码 Agent 会自动修改文件、运行迁移和调用部署工具。只要工作流把“命令退出成功”当成“输入已经完整”，同样的失败模式就会从 shell 历史扩展到配置、数据库、索引和生产资源。
对团队的启发所有覆盖式写入都采用临时文件、完整性校验、fsync 与原子替换；校验必须发生在 rename 或提交之前。对难复现问题添加故障快照和可控崩溃点，core dump 可能包含历史、凭证或业务数据，必须只在受控环境保存。Agent Eval 则要隔离互联网和答案文件，记录提示、Harness、重试和成本。

相关缺陷存在约 10 年，Zsh 5.9.2 已包含修复作者的故障捕获补丁在写入少于 50,000 行时主动崩溃，实际 core dump 显示写到 45,546 行一次截断跟踪中，读取约 11.6 MB 后提前停止，随后同样大小的不完整临时文件覆盖原文件作者报告约三次 Agent Eval 花费超过 300 美元；通过率和 Token 数仅代表该任务、提示与 Harness

我的判断：这起 Bug 最值得复制的不是某个 tracing 工具，而是 fail-stop 设计：当关键不变量无法证明时，停止提交并保留最后一个正确版本。作者后续让模型诊断同一故障也说明，评测真正区分模型的往往不是能否提出正确假设，而是能否持续验证、推翻错误路径并回到证据。

原子写入只能保证替换完整，不能保证你替换进去的是完整数据。

来源：michael.stapelberg.ch

3、Windows 11 天气应用被测出可占用超过 1 GB 内存 reported

4、Claude 生成的 Dark Hours 复现了另一个开源项目的旧 Bug reported

把一千个完整版本压进 80 KB，代价是每次编辑都重写历史

压缩器确实能充当隐式差分器，但一个极小的最终文件可能制造巨大的累计写放大。

Simon Willison 的 AI 生成研究原型把 1,000 个约 20 KB 文本版本压到 80.3 KB，但单 BLOB 方案累计写入耗时 26.8 秒；128 版本分块使用 109.9 KB，将总耗时降到 1.53 秒。

最终文件很小，不代表写入路径很轻。

🛠️ 工具推荐

多端 Agent 控制台P1

T3 Code

T3 Code 是 MIT 许可的 Agent Harness 控制面，提供 iOS、Android、Web、Electron 桌面端与本地服务器，可用 `npx t3@latest` 试跑。适合离开电脑后检查任务、审批动作和切换会话。限制是新任务默认 Full access；远程接入应使用 Tailscale 等私有网络和一次性配对令牌，不能直接把 HTTP 后端暴露公网。项目 README 也明确仍处很早期。

进程因果追踪P1

witr

witr 是 Apache-2.0 的 CLI/TUI，可从进程、端口、容器或文件追踪启动链，并输出机器可读 JSON。支持 Linux、macOS、Windows 和 FreeBSD，适合排查后台服务、测试端口和未知常驻进程。限制是结果依赖操作系统权限与可见性，macOS SIP 和 Windows 受保护进程会隐藏部分环境信息；安装时优先使用包管理器并核验版本。

Go 到 C11P2

Solod

Solod 是 BSD-3-Clause 许可的实验语言与工具链，复用 Go 的模块、LSP、lint 和测试体验，生成无 GC、无隐藏分配的 C11，并提供 C 互操作。适合 Go/C 开发者验证嵌入式或系统组件。限制是 Go 工具不会提示 Solod 不支持的完整语法，泛型支持有限，并发由库提供；生产采用前需固定提交并审查生成代码。

🧠 AI 工具

Monorepo 知识图谱P1

Code-Graph-RAG

Code-Graph-RAG 是 MIT 许可的 MCP 与 CLI，使用 Tree-sitter/ast-grep 建模多语言仓库，将关系存入 Memgraph，并可结合 Qdrant 做语义检索。适合后台、Web、移动端共享的 monorepo 定位调用链和结构化重构。限制是需要 Docker、Memgraph、cmake 与 ripgrep；所有项目共享同一图，`--clean` 会删除整个共享图，敏感仓库还要审查模型与向量配置。

🧩 本期概念库

1. Fail-stop 提交

一句话解释：关键不变量无法证明时立即失败，不让部分结果进入最终状态。

为什么重要：它把可恢复的进程失败和不可恢复的数据损坏分开。

团队应用：覆盖文件、发布索引和数据库迁移前验证输入完整、计数一致，并保留上一个正确版本。

2. 因果进程链

一句话解释：从目标进程向上追踪 shell、服务管理器、容器和定时器，解释它为什么存在。

为什么重要：PID 和端口只描述当前状态，启动链才能定位自动重启、重复服务和错误所有者。

团队应用：故障排查先保留父进程、工作目录、监听地址、容器和服务单元，再决定终止或修改配置。

3. 可执行故障 Eval

一句话解释：把真实故障的源码、症状和跟踪证据封装成隔离任务，用明确根因作为评分标准。

为什么重要：它比通用问答更接近 Agent 在仓库中提出、验证和推翻假设的能力。

团队应用：从已修复 Bug 建立 Eval，隐藏修复提交、隔离网络，并记录重试、成本和错误理论。

4. 依赖播种

一句话解释：依赖者主动保存并传播自己需要的源码副本，让可用性成本由受益方共同承担。

为什么重要：它降低单一代码托管平台故障或消失对构建链的影响。

团队应用：关键依赖使用制品镜像、源码归档或 vendoring，并定期在断网环境验证构建。
