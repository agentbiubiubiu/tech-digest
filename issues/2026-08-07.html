第 74 期：GitHub 恢复了，但漏掉的 push 不会自动回来

第 74 期 · 2026年8月7日，星期五

✨ 本期亮点：GitHub Actions 与 Pages 故障持续约 10 小时 42 分，部分 push 与 PR 触发事件无法自动重放 · Datasette 修复一类可绕过 execute-sql 限制、读取同库私有表的 SQL 注入问题 · AMD 已签署收购 Taalas 的最终协议，但交易仍待惯常交割条件与监管批准 · FLAWED 用真实 CVE、重复采样和交叉验证测试 AI 补丁，但运行不可信代码时需要隔离 Docker 主机 · Jujutsu 0.44 调整 Git 标签的 fetch/push 默认行为，升级前应在沙箱验证发布流程 · X 当日重新传播 Agent Skills 旧课程；官方页面确认主讲为 Elie Schoppik，并非帖子暗示的 Andrew Ng

GitHub 官方事故记录确认服务已经恢复，但部分未处理的 push 与 PR 工作流事件不能自动重放，需要客户主动重新触发。

🎯 本期核心判断：关键交付平台恢复绿灯不等于业务恢复；队列、Webhook 和不可重放事件必须单独对账，而 Copilot 代码评审与 Coding Agent 接入同一控制面后，故障半径已经从 CI 扩展到更多研发环节。

🔥 主故事

绿色状态页能结束事故，只有事件对账能结束业务影响

GitHub 在恢复公告里留下了一句比绿色状态更重要的话：部分 push 和 PR 事件没有被处理，而且无法自动重放。

GitHub 官方时间线显示，Actions、Pages、Copilot 代码评审、Copilot Coding Agent、托管与自托管 Runner、Webhook 以及 Enterprise Importer 都在事故中受影响。8 月 6 日 20:34 UTC，Webhook 处理率仍约为 15%，排队任务成功率约为 65%；之后任务成功率逐步回升到 97% 和 99%，最终于 8 月 7 日 02:04 UTC 宣布恢复。

核心冲突平台可以把服务恢复到可用状态，却无法替团队判断哪些提交、评审、发布和外部通知在中间丢失。只盯状态页的团队会把“基础设施恢复”误当成“交付链完整”。
转折点恢复过程不仅要修 Runner 分配和队列积压，还要面对不可重放事件。GitHub 明确建议受影响客户推送新提交、更新 PR 或手动重跑任务；部分 ARC 用户还需要删除卡住的 Pod 并重新部署。
为什么是现在代码评审 Agent、Coding Agent、CI、Pages 和 Webhook 越来越依赖同一平台控制面。以前一次 GitHub 故障主要拖慢构建，现在还可能让自动评审、代理任务和发布通知同时失联。
对团队的启发建立交付事件账本；服务恢复后按 commit、PR、Webhook 和发布状态执行对账；为热修保留备用构建路径；Copilot 评审或 Coding Agent 不可用时降级到人工流程，而不是阻塞全部合并。

从媒体记录的首次报告 15:22 UTC 到官方恢复 02:04 UTC，约 10 小时 42 分20:34 UTC 时 Webhook 处理率约 15%同一时间排队任务成功率约 65%，此前低点约 30%-40%部分 push 与 PR 触发事件无法自动重放

我的判断：这次事故的根因分析尚未发布，不能归因给 AI。可以确定的是，团队自己的恢复设计必须覆盖“事件没有进入队列”这一类空洞：按 commit SHA、PR 状态和发布记录重新对账，而不是只检查队列是否清空。

绿色状态页能结束事故，只有事件对账能结束业务影响。

来源：www.githubstatus.com

📰 科技动态

1、Datasette 修复混合公私表配置下的 SQL 注入 项目官方发布说明，已证实；作者称受影响配置较少见

表级权限看似隔离，数据库级 SQL 入口却把公开表变成了进入私有数据的跳板。

Datasette 1.0a38 修复一类权限边界漏洞：当同一数据库同时存在公开表和私有表时，拥有任一公开表访问权的用户可能绕过 execute-sql 限制执行 SQL 注入，并以只读方式访问私有数据。0.65.3 也包含修复。

为什么重要：使用 Datasette 的后台应先识别同库混合公私表，再升级并补一条越权回归测试。

事实边界：漏洞只提供只读访问，且需要特定权限组合；不能概括为所有 Datasette 部署均可被远程接管。

60 秒审批游戏暴露 Human-in-the-loop 的脆弱位置

把人放进审批回路并不会自动形成控制；倒计时、重复请求和模糊命令会压缩判断。

The Register 当日采访并报道 ScaleX 的审批游戏：超过 4 万轮、40.9 万次决策中，玩家平均识别约 66.3% 的危险请求，7% 的参与者批准了全部动作。

USENIX Security 面对论文洪峰，先从不存在的引用下手

审核资源被投稿洪峰挤压时，最先可自动执行的规则不是判断作者用了什么模型，而是验证引用是否存在。

USENIX Security 收到 3,030 篇有效投稿，高于上一年的约 2,400 篇。首轮 1,181 篇投稿中，21 篇因至少包含 3 个不存在的引用被拒；组织方没有声称这些引用全部由 AI 生成。

Zig 用阻塞系统调用实现可取消 I/O

异步接口不一定要求每一步都非阻塞；真正难的是取消请求能否被内核中的阻塞调用可靠看见。

文章拆解 Zig 新的 Io.Threaded：底层仍使用阻塞系统调用，但通过共享内存标记、信号、中断后的 EINTR 与确认循环提供取消能力，试图把接口语义与操作系统机制连接起来。

语音钓鱼开始直接打到员工私人电话

企业可以保护工单系统和办公邮箱，却很难阻止攻击者绕到员工私人号码上制造紧迫感。

Google Threat Intelligence 报告称，攻击者冒充同事或帮助台，拨打员工私人电话，引导其在仿冒页面输入凭证和 MFA 信息，再进入企业云环境。Google 将多个品牌暂时归入 UNC6671。

🧩 本期概念库

1. 恢复后对账

一句话解释：服务恢复后，不只检查当前请求是否成功，还要核对故障窗口内所有应发生的事件是否已经产生预期结果。

为什么重要：它能发现没有进入队列、因而不会被普通重试机制看见的空洞。

团队应用：按 commit SHA、PR、Webhook ID 与发布版本生成待核对清单。

2. 事件重放缺口

一句话解释：事件在持久化或进入队列前丢失，平台没有足够记录自动重建原始动作。

为什么重要：队列清空和错误率归零都无法证明这类事件已经补齐。

团队应用：保存业务侧事件账本，并提供幂等的人工重放入口。

3. 语义补丁正确性

一句话解释：补丁不仅要通过现有测试，还要消除原 exploit、保持合法行为并避免引入新漏洞。

为什么重要：生成式模型很容易给出表面合理、局部测试通过的修改。

团队应用：将 exploit 回归、行为差异、静态分析与重复采样组合进评测。

4. 审批疲劳

一句话解释：人在高频、低信息量或有时间压力的确认中逐渐形成机械批准习惯。

为什么重要：Human-in-the-loop 只有在信息足够、风险分层和可拒绝时才形成真实控制。

团队应用：合并低风险确认，高风险动作突出目标、数据流和不可逆影响。

🎲 还能这样？今日好奇心

把 PID 控制器放进电子表格

不用先推公式，改三个增益就能看见系统如何追上目标、过冲和恢复。

作者在 Google Sheets 中模拟被控对象与 PID 控制器，用 0.1 秒步长观察 Kp、Ki、Kd 和扰动对输出的影响。它是教学模拟，不连接真实硬件。

背后的启发：把抽象控制问题做成可操作反馈，比只背参数定义更容易形成直觉。

铷频率标准如何把振荡器锁到原子跃迁

稳定时钟不是让晶振永远不漂，而是持续用原子信号把它拉回正确位置。

文章拆解铷-87 频率标准的三类单元，并解释如何利用约 6.835 GHz 超精细跃迁产生误差信号，再反馈校正振荡器。

背后的启发：高可靠系统通常不追求部件绝对不漂，而是设计可观测、可校正的闭环。

PhantomDrive 在同一 U 盘里藏第二个文件系统

公开分区里写入一段特定内容，固件才会切换到隐藏的加密存储。

这个开源实验项目用 CH569 处理 AES-256，并根据写入公开分区的 `password:` 指令解锁隐藏文件系统。作者明确表示它没有经过专业安全审计。

背后的启发：有趣的隐蔽机制不等于可依赖的安全产品；密钥处理、侧信道和取证痕迹仍需审计。
