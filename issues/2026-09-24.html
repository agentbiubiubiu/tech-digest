第 106 期：百万行 PR 的真正难题是证明它没坏

第 106 期 · 2026年9月24日，星期四

Agent 让大规模改动更容易发生后，交付瓶颈会从“能否生成”转向“能否观察、重放并判定运行时行为”；复杂 UI 应先建设健康信号与自动化预算，再扩大改动规模。

🔥 主故事

百万行 PR 的难点，是把偶发卡顿变成可判定失败

二千二百个文件、超过一百万行改动、四百多条行内评论，只有约一百行会在任一时刻真实存在于 DOM。

GitHub Copilot App 团队用可找到的极端开源 PR 验证新差异界面；常规虚拟列表在评论异步加载、折叠区和动态高度面前会出现白条、跳动与难复现卡顿。

核心冲突Agent 让八十万行级重写更可负担，但改动越大，人工滚动抽查越无法证明界面在冷启动、热缓存、展开、回复与缩放组合下仍可靠。
转折点团队把候选工作限制在视口附近约2400像素，接入React渲染次数、性能时间线和逐帧采样，再用声明式流程驱动无头探针与真实桌面应用循环；健康信号最终成为端到端预算。
为什么是现在生成吞吐提高会放大大规模迁移与重构的频率，验收若仍依赖肉眼，就会成为新的交付瓶颈。
对团队的启发从一个高状态密度界面建立最小探针：固定操作流、记录节点与长帧、定义预算、在真实应用回放；不要把极端PR当作鼓励大提交。

2200个文件超过100万行改动400+条行内评论约100行DOM同时存在视口附近约2400px进入候选

我的判断：新增认知不是“使用虚拟列表”，而是把运行时可观察性设计成验收接口。先让复杂状态可重放、可度量、可失败，再让Agent扩大改动范围。

Agent 扩大了可改范围，健康信号决定了可交付范围。

权限边界方法可试

本地Agent沙箱核验清单

把文件、网络、凭据、会话生效时点和失败关闭逐项验收，而不是只看“已开启”。

适合你的环节：本地Agent任务启动前

今天怎么试：在隔离项目启动新会话，尝试一个被拒目录和被禁网络目标，确认明确失败且无副作用。

边界：Copilot App功能本身默认关闭、仅影响本地仓库与工作树会话，仍为公开预览；方法可迁移。

采用判断：今天先借鉴核验清单，不因预览功能迁移工具。

当前做法：当前Codex任务已有沙箱与最小授权规则，但具体项目策略状态未知。

新增收益：新增的是把生效时点和失败关闭纳入验收，避免配置存在却未执行。

验证标准：被拒访问必须稳定失败；允许路径、正常测试与Git只读操作不得退步。

🧩 本期概念库

1. 健康信号

一句话解释：把渲染次数、长帧、请求、节点数量和业务结果压成可自动判定的状态。

为什么重要：没有健康信号，自动回放只能证明脚本跑完。

团队应用：先定义失败预算，再写驱动流程。

2. O(viewport)渲染

一句话解释：工作量随当前视口附近内容增长，而不是随整个数据集增长。

为什么重要：百万行数据仍能保持有限DOM与布局成本。

团队应用：同时验收滚动定位、动态高度和评论异步加载。

3. 失败关闭

一句话解释：安全策略无法执行时停止运行，而不是退化为无保护模式。

为什么重要：避免“配置看起来存在、实际没生效”的隐性风险。

团队应用：把策略执行失败加入启动验收。

4. 输出分布验收

一句话解释：比较输出长度、位置、完整度和用户行为，而非只看平均正确率。

为什么重要：相同离线分数可能产生完全不同的编辑体验。

团队应用：模型升级保留固定样本与分布对照。

🎙️ 播客提纲

展开口播稿

百万行 PR 教会我们的，不是如何渲染更多 DOM

一个包含二千二百个文件、超过一百万行改动和四百多条行内评论的拉取请求，真正难的不是把它打开，而是证明用户滚动、展开、回复和缩放时，界面仍然没有悄悄坏掉。

主故事：从百万行差异到可验证界面

GitHub Copilot App 团队拿一个极端拉取请求做压力场景：二千二百个文件、超过一百万行改动、四百多条行内评论。浏览器不可能挂上一百万个 DOM 节点，所以它只让视口附近约二千四百像素范围内的区块进入候选，实际同时存在的行大约一百条。难点是评论、折叠和异步加载会不断改变高度，肉眼偶尔滚一遍无法复现白条、跳动和延迟。团队因此把 React 渲染次数、性能时间线和逐帧卡顿采样接入生产埋点，再用声明式 JSON 流程驱动无头探针和真实桌面应用。真实应用的自动循环会分别走冷启动和热缓存，展开详情、打开再取消回复框、切换文件树并改变窗口大小；测量结果同时写入磁盘，让Agent不需要盯着屏幕也能读回运行时证据。每个样本带健康信号，端到端测试把它们写成预算。这里有个容易忽略的边界：可重放不等于可信。如果脚本只检查按钮点过、页面滚过，它仍会放过卡顿、错位和异步状态丢失；健康信号必须直接对应用户能感知的失败。新增认知不是虚拟列表本身，而是 Agent 让大规模重写变得可行后，验收系统必须先能观察、重放并判定失败。文章是单团队案例，百万行是极端样本，不代表日常 PR 应该变大。

快讯一：沙箱必须失败关闭

GitHub Copilot App 的本地沙箱可以按项目限制文件、网络和凭据，但默认关闭，只影响新会话或重启后的会话。最重要的一条是：操作系统无法执行策略时，沙箱 shell 会报错，而不是无保护运行。它仍是公开预览，云端和远程主机也不受这组设置控制。

快讯二：共享规则要用金丝雀验证

一名工程师实测 Claude Code 的 AGENTS 点 MD 支持曾受远程开关和非必要流量设置影响，规则文件会静默不加载；其文章后来标记已修复。可迁移的方法是为关键规则放一个无害金丝雀，并在版本升级或隐私设置变化后检查它是否真的生效。单篇复现不能替代官方兼容承诺。

快讯三：数据库测试要跑真实语义

pgsql-test 把临时数据库、事务回滚、角色与 JWT 上下文放进 JavaScript 测试循环。它强调 mock 无法验证外键、触发器、行级安全和真实数据库角色。适合已有 PostgreSQL 逻辑的项目小范围试验，不能仅因示例顺手就引入新依赖。

行动：给一个复杂界面补可重放健康信号

今天最值得采取的动作，是从一个容易卡顿或状态错乱的列表、图表或差异页选一条真实操作流，记录视口节点数、长帧、关键请求与交互结果，做成可重放脚本。先只覆盖一个冷启动和一个热状态，不做无意义的全排列；再故意注入一次超预算延迟或错误高度，确认探针真的会失败。成功条件不是跑完，而是同一类回归能稳定失败、修复后稳定通过，并且正常场景没有明显变慢。若现有监控已经能给出这些证据，就不需要为新工具重建一套体系。

当 Agent 把改动规模推高，真正稀缺的不是生成能力，而是能让运行时问题被观察、重放和判定的验收系统。
