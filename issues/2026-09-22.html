第 104 期：当代码生成变快，CI 接管了交付节奏

第 104 期 · 2026年9月22日，星期二

当编码 Agent 提高变更吞吐后，应优先优化端到端验证反馈、分片均衡与失败回读，而不是继续只追求更快生成。

✨ 本期亮点：Linear 单团队案例：8 分片让关键任务初测快约19%、成本低约19% · 9项个人工具与方法：3项方法可立即试，6项需项目、账号或版本条件 · Jev 把开放式文本生成收窄成结构化概率输出，但仍缺可靠公开比较 · tokenizers v1 候选版报告3-30倍单线程编码提升，采用前先证明分词真是瓶颈

来源：Linear 工程文章；性能与成本数字来自其自身代码库和基础设施，未独立复现。

🔥 主故事

代码供给暴涨后，验证系统成了新的排队口

每周约新增 2,000 个测试，PR 仍要经过同一条 CI 管线；写得更快并不自动等于交付更快。

Linear 工程师收到 CTO 指派的“CI costs are high”任务：既要压低成本，也要缩短等待。Agent 加快了代码产生速度，但测试、类型检查和 runner 调度没有同步扩容。

核心冲突最直接的反应是加机器，但不均衡分片会让快 runner 等最慢 runner；更高并发还可能只把成本放大。真正约束合并速度的是关键路径，而不是总算力。
转折点团队拆分大测试文件并重排分片；从四分片到八分片的初测让关键任务速度和成本均改善约19%，一周后最慢分片从5.25分钟降至4.33分钟。tsgo 又把 TypeScript 检查周中位耗时降低73%，瓶颈随之转移。
为什么是现在编码 Agent 正把“产生更多变更”变成常态。若验证反馈仍慢，Agent 和人都会在排队、重试与上下文切换中消耗新增吞吐。
对团队的启发从最近20个 PR 建一张验证关键路径表，先找最慢分片、最高波动与重复重试；没有瓶颈证据就不扩容。

每周约新增2,000个测试8分片初测约快19%且便宜19%最慢分片5.25分钟降至4.33分钟tsgo让类型检查周中位耗时降73%

我的判断：这不是“所有团队都该翻倍分片”的结论。可迁移的是先测排队、执行、重试和最慢分片，再针对关键路径做同输入对照；只有端到端时间下降、失败检出不退步且成本可解释，优化才成立。

Agent 增加的是变更供给，CI 决定的是这些变更多久能变成可信交付。

来源：linear.app

🧩 本期概念库

1. 验证供给

一句话解释：CI、测试环境和人工回读能够消化多少变更。

为什么重要：生成吞吐超过验证供给时，排队和上下文切换会吞掉Agent收益。

团队应用：同时追踪PR生成量、排队时间、重试率和端到端交付时间。

2. 关键路径优化

一句话解释：只优化决定最终完成时间的最慢依赖链。

为什么重要：加速非瓶颈步骤不会缩短总等待，甚至可能提高成本。

团队应用：按P50/P95和分片尾部耗时定位瓶颈，再做单变量对照。

3. 决策模型

一句话解释：把自然语言输入映射为类别、概率或分数，而非继续生成文本。

为什么重要：输出更易接入程序，但可信度取决于校准和错误成本。

团队应用：用真实样本比较校准误差、拒答阈值和业务损失。

4. 瓶颈迁移

一句话解释：一个步骤加速后，系统上限转移到下一慢的步骤。

为什么重要：局部性能胜利不等于端到端收益。

团队应用：每次优化后重新测整链路，不沿用旧瓶颈假设。

🎙️ 播客提纲

展开口播稿

代码越来越快，为什么交付反而卡在等待上

Linear 每周新增大约两千个测试。Agent 把写代码推快之后，每个 PR 仍要排队经过 CI，验证速度没有同步增长。今天真正值得理解的，不是哪一个模型又快了，而是当生成不再稀缺，测试调度、反馈时延和失败回读会接管整个交付节奏。

主故事：瓶颈从生成移到验证

Linear 的工程师接到一个很朴素的任务：CI 成本太高，也要更快。问题的起点不是某个测试突然变慢，而是 Agent 让代码和 PR 更快出现，所有变更仍要经过同一条验证管线。团队先拆分过大的测试文件，再重新评估分片和 runner。把三到四个分片进一步增加到八个后，初始基准中的关键任务快约百分之十九、成本低约百分之十九；一周后最慢分片从五点二五分钟降到四点三三分钟。另一次工具链更新把 TypeScript 检查的周中位耗时降低了百分之七十三。这里的机制不是简单加机器，而是让工作分布更均衡，并把关键路径上已经不再最慢的步骤移出优化焦点。团队还估算，如果年初不主动治理，当前测试套件可能需要约十一分钟，接近现在等待时间的两倍。但这些数字来自 Linear 自己的代码库、负载和成本模型，没有独立复现，也不能直接成为我们的扩容预算。

快讯一：Decision Model 把输出从文本改成概率

Jev 接受文本输入，却返回类别、真假判断、评分和置信度等数值，而不是继续生成一段话。它把一类决策任务从开放式生成收窄成结构化输出。当前宣传的价格与速度仍来自项目方，公开基准也容易被针对性优化。更稳妥的试法，是拿一个真实分类任务，与现有小模型比较校准误差、拒答策略和错误成本。

快讯二：Agent 自动路由要看账单回退

Claude Code 二点一二七八把多种 API、企业和云网关场景的 Auto mode 默认切到服务端分类器，并在状态页显示分类位置，同时提示计费回退。采用价值不只是自动选模型，而是让路由位置和异常路径可观察。若正在使用对应版本，升级验收应同时核对实际模型、延迟、回退和费用。

快讯三：Tokenizer 也会成为吞吐瓶颈

Hugging Face 报告 tokenizers v1 候选版本在十个模型家族上，单线程编码相对零点二三版快约三到三十倍，并保持相同 token ID；八 worker 扩展效率为线性的百分之七十六。它仍是候选阶段，覆盖范围也有限。只有当 profiling 证明 CPU 分词让 GPU 等待时，升级才有实际价值。

行动：先画出交付关键路径

今天最值得做的一件事，是从最近二十个 PR 取出排队、执行、重试和人工等待时间，按检查项画出关键路径。先找最慢分片、最高波动和最常见重试原因，再用同一批 PR 做一次对照。成功条件不是机器更多，而是端到端等待下降、失败检出不退步、成本可解释。如果当前没有明显排队或分片失衡，就无需照搬 Linear 的架构。

今天的一句话：Agent 提升的是变更供给，真正决定交付速度的，是验证反馈能否跟上。先测关键路径，再优化瓶颈。
