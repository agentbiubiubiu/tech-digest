🔥 主故事

Agent 做对一次，还会连续做对吗？

同一条任务，演示时做对，换一次运行却失败。平均成功率可能把这种波动藏了起来。

IBM Research 在9月15日的文章中比较两种指标：重复运行后的平均成功率，以及每次重复都成功的任务比例。其 AppWorld 实验中，一个 GPT-4.1 ReAct Agent 的前者为77.4%，五次都成功的任务比例为53.0%。

核心冲突两者相差24.4个百分点，但不是模型突然退步：它们问的是不同问题。一个数关注总体平均，另一个数关注同一任务能否稳定重复完成。
转折点作者进一步用 Consistency Analyzer 对一条已记录的执行轨迹中的决策点重新采样，寻找容易改变选择的步骤。它不需要真实答案来定位决策波动，但这不等于无需答案就能证明任务正确。
为什么是现在这篇新研究给日常 Agent 验收一个更具体的问题：除了成功截图，还应检查同一输入的重复行为，以及在哪个决策点出现变化。
对团队的启发选一个只读、脱敏、可重放的任务，固定输入和环境，分别记录平均结果与重复稳定性；有副作用的流程先用测试替身。

我的判断：我的判断：复杂度不高时，先把验收条件写清、用受控重复观察波动，比马上换更强模型更容易解释问题。对会发消息、写数据或触发交易的任务，不能在生产环境反复执行来做实验。

一次成功是结果，稳定成功才是能力边界。

diagnosing-bugs Skill：先固定能判失败的反馈

已有排障 Skill 把稳定、可重复的失败信号放在猜根因之前。适合偶发页面异常、接口条件错误或性能回归：先说清什么输出才算问题出现，再提出和排除假设。经典方法，不是今天新发布。

适合你的环节：减少 Agent 读很多代码后凭猜测改动，以及“没报错就算修好”。

今天怎么试：直接说：“用 diagnosing-bugs 分析这份脱敏错误证据，先设计最小复现和判定条件；不改业务代码、不构建，待我确认再执行。”

边界：当前可调用不代表已经复现你的问题。生产插桩、压力测试、设备运行和写操作仍需明确授权；证据不足就报告缺口。

实践精选已有能力可用

codebase-design Skill：检查接口是否把复杂度推给调用方

已有 Skill 关注用较小接口承载完整行为，把状态、错误和约束放到合适位置。对客户端与后台共享逻辑，它可以帮助识别“每个调用点都得知道同一堆细节”的设计问题。

适合你的环节：减少跨端接口使用规则散落、同一修复需要改多个调用方的维护成本。

今天怎么试：直接说：“用 codebase-design 看这个模块接口，列出调用方必须知道的条件和可隐藏的复杂度，先提方案，不重构。”只提供相关接口和两个调用点。

边界：不是越少函数越好，也不自动要求抽象或迁移。方案需要结合现有边界、真实调用方式和可测性，不能只凭代码长度判断。

实践精选方法可试

git range-diff：比较两轮提交方案

当 Agent 按审查意见修改了一组提交，用 range-diff 比较两轮补丁序列，可辅助看出修订是否改变原意。它不是普通工作区 diff 的替代品，更适合已有旧、新提交范围的复审。属于经典方法。

适合你的环节：缩短 rebase 或第二轮修订后，从头重新审查全部提交的时间。

今天怎么试：先保留两轮真实提交边界，再只读比较 old-base..old-tip 与 new-base..new-tip；让 Agent 解释新增、丢失和改变的补丁。没有旧边界时先补记录，不猜范围。

边界：只证明补丁对应关系，不证明行为正确；拆分或合并提交时需人工解读。没有执行 rebase、改写历史或强推；不包含未提交改动。

🧩 本期概念库

1. 一致性差距

一句话解释：平均运行成功率与重复全部成功任务比例之间的差异，需说明实验和重复次数。

为什么重要：均值不能回答每个任务是否可靠。

团队应用：只在可控、无业务副作用的流程记录重复结果。

2. 证据保留

一句话解释：压缩输入时保留能支持判断、复现和验收的信息。

为什么重要：上下文更短不自动意味着回答更准确。

团队应用：先定义必须保留的错误、输入和环境条件。

3. 副本亲和

一句话解释：让关联请求落到同一个副本，以访问该副本上的会话状态。

为什么重要：会话存在与请求到达正确节点是两件事。

团队应用：联调时核对请求落点，不只检查HTTP成功码。

你有没有遇过这种情况：昨天让 Agent 做同一件事成功了，今天再来一次，却卡在另一处？九月十六日的日报讨论一个容易被演示掩盖的问题：平均表现不错，不等于每次都可靠。今天同时筛选八项工具，重点放在上下文成本、代码理解和可检查的研发流程。

主故事：平均成功率藏住了什么

IBM Research 的新文章把同一组任务重复运行，再分别看两个数。一个是所有运行的平均成功率，另一个是五次运行都成功的任务比例。文章中一个 GPT-4.1 Agent 在指定 AppWorld 实验下，平均成功率是百分之七十七点四，五次都成功的任务比例是百分之五十三。这是研究团队的基准结果，我们没有独立复现，也不是你的任务成功率。这两个数并不矛盾：有些任务时好时坏，就能抬高平均值，却不能算稳定通过。作者还介绍了对执行轨迹中的决策点重新采样，用来找容易改变选择的步骤。没有真实答案也能发现选择不一致，但不能因此证明答案正确。对我们更实用的动作是，固定输入、环境和验收条件，选一条只读、脱敏、能重放的链路。不要在生产环境重复发消息、改数据或触发交易，只为了测试 Agent 是否稳定。

快讯一：减少无效输入，不压缩必要判断

Context Mode 是今天最值得单独评估的候选。它管理进入 Agent 上下文的工具输出和路由，适合你关心的长日志、重复抓取和无效上下文问题。但尚未接入，不同客户端的 hook 能力也不同。我们不采用项目宣传的省 Token 比例。先拿一份脱敏样例，记录必要证据是否保留，再看实际运行用量。节省不应该靠隐藏限制，或者把最终答案强行缩短。

快讯二：代码图谱也有看不到的地方

Graphify 提供局部代码与资料的关系图，仓库说明 code-only 可以采用本地 AST 提取。它适合辅助理解陌生模块，但图里没有一条边，不证明运行时不会调用。反射、动态注册和路由仍要结合原始代码与运行证据。先评审来源，再用非敏感小样例核对一条已知调用链。不要直接扫完整业务仓库，也不要把图谱结果当成可以删文件的批准。

快讯三：流程包不是装完就生效

Ponytail 倾向减少过度实现，gstack 把评审和 QA 做成角色，Addy 的 Agent Skills 把研发检查组织为流程。它们都还没有安装。值得注意的是，单独复制一个 Skill 可能漏掉仓库级参考资料。命令能出现，并不表示全部检查清单都能访问。先和现有能力比缺口，不要同时叠加几个互相冲突的流程包。少写代码也不能少掉必要校验和错误处理。

今天可以直接做的三件事

第一，用已有的 diagnosing-bugs Skill 设计最小复现与判定条件，先不改业务代码。第二，用 codebase-design 看一个模块的接口，找出哪些复杂度被迫交给调用方，先提方案。第三，如果手里有两轮真实提交范围，用 git range-diff 只读比较补丁修订，而不是重新看整份改动。它们分别回答问题怎样复现、设计怎样收敛、修改有没有偏离原意。今天没有构建业务项目、安装新工具或改写 Git 历史。

今天的结论是，把一次成功变成可重复的证据，比继续增加 Agent 更重要。在线版有十八条正文和八项工具，明确区分已有能力、方法可试和需接入。口播是文字稿，时长为估算，没有生成或试听音频。

✅ 对团队的启发

1

用 diagnosing-bugs 为一处问题写清最小复现和失败信号，先不运行业务构建。

2

用 codebase-design 评估一个接口，保留原实现，只讨论复杂度放在哪里。

3

有两轮提交范围时再用 git range-diff 比较修订；不要为试工具改写历史。
