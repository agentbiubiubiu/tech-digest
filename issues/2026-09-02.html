第 88 期：Claude 写下 18 万行代码，作者却说自己审不完

第 88 期 · 2026年9月2日，星期三

✨ 本期亮点：Paint.NET 作者 Rick Brewster 披露 Claude 为 WINE 路径生成约 18 万行 Direct2D 兼容代码，同时承认无法全面审查；这是作者陈述，不是独立代码审计 · Vercel 官方称 AI SDK 软件工厂运行四周后贡献每周合并 PR 的 25%-35%，并关闭 70%-80% 的问题；这些比例属于团队自报数据 · Flue 与 tldraw 都把外部 PR 转回问题或讨论，说明开源贡献的稀缺资源正在从代码转向上下文、判断和持续跟进 · Anthropic 发布 Claude Fable 5.1 与受限访问的 Mythos 5.1；价格与 Benchmark 均按厂商口径处理，不作独立性能结论 · BenchMIRT 用 100 个开源模型、16 个基准和 3.4 万余题分析单一分数混合了哪些能力，提醒团队先验证指标测量的对象 · X 当日抓取成功；GitHub Copilot 模型可用性与免费课程传播均回到官方文档核验，未证实的“18 门课程”没有写成事实

配图来自 Vercel 软件工厂官方工程文章。

🔥 主故事

当 Claude 写下 18 万行代码，真正缺的已经不是更多代码

Rick Brewster 想让 Paint.NET 在 WINE 上工作，但 Direct2D 一直是最大障碍。最后，项目没有等待兼容层补齐，而是让 Claude 写了一套内部、洁净室方式逆向实现的 Direct2D 替代层。

Brewster 说，这个程序集大约有 18 万行代码；Paint.NET 其余部分约 70 万行，是他二十多年积累的结果。新代码让过去几乎不可能完成的兼容路径出现了，但他也直言大部分属于“先相信再说”的生成代码，无法进行全面人工审查。

核心冲突Agent 可以持续生成、重试和逆向，人的审查时间却没有同步扩容。Brewster 仍需盯住 COM 引用计数、资源管理和架构选择；他举例称 Claude 一度没有正确执行类似 `AddRef()` 的操作。交付速度提高后，未被理解的状态、边界和故障模式会迅速累积。
转折点一些团队没有继续堆更多 Agent，而是重写入口和证据链。Vercel 为 AI SDK 建立分类、复现、实现、审查和回移植的专职 Agent，每一步运行在隔离沙箱中，最终仍由人合并。Flue 自动关闭外部 PR，把贡献转换成问题或讨论；tldraw 也暂时关闭未经邀请的外部 PR，理由包括上下文不足、误导性修改和缺少后续跟进。
为什么是现在AI 把代码生成的边际成本压低后，项目会先遇到注意力过载，而不是算力不足。Vercel 官方披露其 AI SDK 曾积压超过 1000 个问题和近 800 个 PR；软件工厂上线四周后，团队称 Agent 编写每周合并 PR 的 25%-35%，并关闭 70%-80% 的问题，但所有合并仍保留人工控制。
对团队的启发把 Agent 交付从“生成一段代码”改造成有状态流水线：先分类风险，再要求最小复现；实现必须附测试、截图、日志或接口回读；公共输入进入隔离沙箱且只拿任务所需凭证；低风险文档可快速审，高风险 API、资金、安全与迁移必须深审；每个失败都沉淀为新的规则、上下文或评估样例。

18 万行：Paint.NET 作者披露的 Claude 生成 Direct2D 兼容层规模，未经过独立审计1000+ / 近 800：Vercel 官方披露的软件工厂上线前 AI SDK 问题与 PR 积压峰值25%-35%：Vercel 团队自报软件工厂运行四周后每周合并 PR 中由 Agent 编写的比例

我的判断：我更关注的不是 18 万行这个产量数字，而是作者公开承认自己审不完。代码生成越快，团队越应该减少不必要的代码入口，并把人类判断集中在问题选择、风险分级和最终责任上。

Agent 扩大的是执行带宽，组织必须自己扩大证据带宽。

来源：simonwillison.net

📰 科技动态

1、Firefox iOS 内置广告拦截，但默认关闭且不会挡住所有广告 official_release

iOS 浏览器不能像桌面端那样自由安装扩展，Mozilla 于是把拦截器直接做进了浏览器。

Mozilla 官方说明，该功能使用 Apple WebKit Content Blocker 与 EasyList，在加载前拦截多种第三方广告和相关跟踪器，可在设置中开启。站点自营广告、搜索广告和 Firefox 新标签页赞助内容不受影响。

为什么重要：iOS 客户端与 Web 团队可以把它当作内容拦截兼容基线：页面不能依赖第三方广告脚本才能完成布局、登录或支付流程。

事实边界：功能、默认关闭状态和限制由 Mozilla 官方确认；“更快”“更省流量”等效果没有独立测量，本期不作性能承诺。

2、AfterQuery 据报道获 32 亿美元估值，交易金额与完成状态仍未由公司确认 reported_round_not_company_confirmed

一家为模型训练专业工作流程的公司，五个月前公开估值还是 3 亿美元，如今报道数字提高了十倍以上。

TechCrunch 转述 Forbes 称 AfterQuery 新一轮融资估值达到 32 亿美元；报道没有给出本轮金额，AfterQuery 未及时回应。该公司 4 月曾宣布 3000 万美元 A 轮及 3 亿美元估值。

为什么重要：这类公司出售的不只是标注数据，而是医生、律师等专业人士的决策过程。对 AI 产品团队，训练数据采购正在从“答案量”转向“可复现工作流”。

事实边界：32 亿美元估值和“最快独角兽”均为媒体报道及相关人士说法，不等于公司公告、已签署交割文件或监管确认；本期不推断交易已完成。

一个尚未全面发布的模型，已经被公司描述为能在无人指导下发现并利用未知漏洞。

为什么重要：安全团队需要同时升级模型访问控制、隔离环境、凭证最小化、输出审计和漏洞披露流程，不能只依赖模型侧拒答。

事实边界：发布状态、能力、Benchmark 和两个零日均来自 TechCrunch 对 OpenAI 材料的转述，缺少第三方复现；“很快”不是确定发布日期，也不代表高级能力会公开提供。

🤖 AI 相关

1、Claude Fable 5.1 与 Mythos 5.1 共用底层模型，用访问与安全策略区分场景 official_release_vendor_benchmarks

同一个模型被拆成通用版本与受信任访问版本，差异不在参数，而在谁能调用哪些高风险能力。

Anthropic 宣布 Fable 5.1 已普遍可用，Mythos 5.1 面向网络安全与生命科学的受信任访问项目。公司估算典型按 token 计费工作负载成本降低约 25%，高度 Agent 化任务最多约 45%，主要来自缓存读取降价。

为什么重要：开发团队选模型时应按任务成本、缓存命中、风险权限和数据保留分别评估，而不是把“同一底模”理解成“同一产品边界”。

事实边界：价格节省、Terminal-Bench、科学研究与安全数据均为 Anthropic 自己的发布与评估；没有独立 Benchmark 支持本期作横向冠军结论。EFS 仍按阶段推出，不等于所有企业客户今天已可用。

2、BenchMIRT 不再只问模型得几分，而是追问每道题实际测了什么 research_team_report_with_open_code_and_data

一套名义上测安全的题目，可能主要奖励一般推理；把它们平均成一个数字，会把信号混在一起。

Ai2 团队介绍 BenchMIRT：基于多维项目反应理论，分析 100 个开源 LLM、16 个基准和超过 3.4 万道题，在模型与题目层面分离安全、推理等潜在能力。团队称，在这些基准中保留信息量最高的 10% 题目，通常仍能保持相近的模型强弱图景。

为什么重要：做模型选型时，可把总分拆成与真实任务相符的题组，再观察成本、失败类型和稳定性；否则排行榜提升可能只是测量对象漂移。

事实边界：方法、样本量与结果来自 Ai2 研究团队文章，代码和数据公开；“10% 题目通常保持图景”只适用于其分析集合，不代表所有 Benchmark 都能缩减 90%。

📝 文章推荐

Dan Luu 把 AI 怀疑论从态度争论改成可回看的预测记录

与其争论一个人“乐观还是悲观”，不如把过去的明确预测、截止时间和后来发生的事情排在一起。

Dan Luu 回查 Ed Zitron 多年来对 AI 公司、基础设施和产品的预测，并先披露自己的投资与立场偏差。文章的价值不在替任何阵营判胜负，而在展示如何把宏大叙事转成可证伪陈述。

观点可以很响，预测必须留下日期、条件和可观察结果。

一篇给程序员的谓词逻辑速成，把规格里的含糊词变成可检查表达式

程序员天天写返回布尔值的函数，却经常在需求里接受无法证明真假的句子。

Hillel Wayne 从谓词、蕴含、集合和量词讲起，强调数学谓词只定义真假，不必同时给出计算方法。它适合用来澄清权限、状态机、不变量和测试条件。

先把“应该如此”写成谓词，团队才知道该证明什么、该测试什么。

“Claude 的无尽诱惑”提醒：效率问题有时并不是技术问题

当工具承诺让人完成更多事情，真正需要回答的也许是：这些额外功能是否值得拥有和维护。

作者从 Paint.NET 的 WINE 工作切入，质疑把个人时间、职业焦虑和产出欲望都交给 Agent 解决。文章是价值判断，不是生产率研究；它提供了主故事之外的重要反方视角。

除了“还能做多少”，产品也需要问“哪些事情根本不必做”。

🧩 本期概念库

1. 审查吞吐

一句话解释：单位时间内，团队能真正理解、验证并负责的变更量，而不是能看到多少 PR。

为什么重要：Agent 提高生成速度后，审查吞吐会成为交付上限。

团队应用：记录从提交到完成复现、风险分级、测试回读和人工批准的各阶段耗时。

2. 软件工厂

一句话解释：由多个职责单一的 Agent 和自动化组件串联分类、复现、实现、审查与发布证据。

为什么重要：它把一次性提示改成可观察、可重试、可改进的生产流程。

团队应用：先从分类与复现两个低风险步骤开始，稳定后再扩展到实现和回移植。

3. 证据带宽

一句话解释：自动化每完成一步，向审查者返回多少可复核的测试、日志、截图、差异和读回结果。

为什么重要：没有证据带宽，生成带宽越高，认知债务累积越快。

团队应用：把失败测试、运行截图、接口响应和影响范围设为 Agent 交付的必填项。

4. 多维项目反应理论

一句话解释：根据不同模型在不同题目上的表现，估计多个潜在能力以及每道题对这些能力的区分度。

为什么重要：它能揭示一个 Benchmark 总分混合了哪些能力，而不只给出排名。

团队应用：把内部评估题按真实业务能力重分组，检查总分提升是否来自目标任务。

5. 贡献入口重构

一句话解释：把外部贡献从直接提交实现，改为先提供问题、复现、约束和讨论，再由可信执行链产出代码。

为什么重要：它降低维护者被迫审查上下文不足代码的成本，但也可能削弱新人学习路径。

团队应用：保留问题模板、复现脚本和讨论入口，并明确怎样从贡献者成长为可信维护者。
