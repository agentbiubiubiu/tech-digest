第 103 期：Agent 的上限，藏在最长的验证链里

第 103 期 · 2026年9月20日，星期日

选择和管理编码 Agent 时，应把端到端可交付率、验证链与返工成本置于单次补丁质量之前。

✨ 本期亮点：Android Bench 2.0：长周期任务最高通过率约28%，明显低于原始短任务约91% · 8项工具与方法：4项方法今天可试，4项需账号、项目或安装条件 · Claude Code Auto mode 把分类器位置、计费回退和状态可见性带入升级验收 · OpenTelemetry 迁移与 AI 写作都指向同一原则：保留接口，逐段验证，再交责任

来源：Android Developers Blog；通过率为该基准配置下结果，不能直接外推到具体业务项目。

🔥 主故事

补丁看起来完成了，App 为什么还没交付？

把任务从一次修补拉长到多天工程，最高通过率从约 91% 掉到约 28%。

Google 在 Android Bench 2.0 中加入首批长周期任务：升级依赖、实现完整功能、从零构建应用，以及把跨平台应用迁到 Android。它们要求 Agent 跨越多个文件、工具和验证阶段。

核心冲突短任务容易用局部 diff 证明进展；长任务却必须持续维护假设，并在编译、运行、依赖图和最终行为上闭环。局部正确不再等于任务完成。
转折点官方观察到模型尤其容易在运行时验证、破坏性框架变化和未发布库知识上失败；跨平台迁移也没有模型达到完全通过，前沿模型最高约80%完成度。
为什么是现在编码 Agent 已能承担更长工作，但团队的委派与验收仍常停留在“代码已生成”。移动端项目的真实门槛是工程可构建、App 可安装、关键状态可回读。
对团队的启发把编译、安装、启动、关键页面回读和异常路径写进移动端 Agent 的完成定义；任何一环缺证据，都不算交付。

原始任务最高约91%长周期任务最高约28%跨平台迁移前沿模型最高约80%完成度

我的判断：这不是“Agent 只能做两成八任务”的普遍结论。它更像一个验收警报：任务跨度增大后，错误会沿依赖链累积，缺失运行证据时尤其容易误判完成。选择模型和工作流时，应比较端到端通过率、耗时与人工返工，而非只看一次补丁。

最长的验证链，决定了 Agent 真正能走多远。

来源：android-developers.googleblog.com

移动端验收方法可试

长任务完成定义矩阵

把编译、安装、启动、关键状态回读和异常路径变成 Agent 的强制交付证据。

适合你的环节：iOS/Android 功能、依赖升级、跨平台迁移与复杂修复

今天怎么试：选一个真实移动端任务，先写5项完成证据，再让现有 Agent 执行；缺任一项按未完成计。

边界：需要可控测试环境；真实资金、生产账号或不可回滚数据不应交给自动化；基准结果不能替代本项目实测。

采用判断：优先采用规则，不引入新平台；先在一个非生产任务上做同输入对照。

当前做法：当前已有移动端构建与 sim-use 验证能力，但具体项目是否统一记录完成证据未知，画像更新于2026-09-17。

新增收益：把“生成代码”升级为“交付可运行结果”，直接减少长任务假完成。

验证标准：同任务记录端到端完成率、总耗时、人工返工；不得减少真实设备或关键业务路径的必要验收。

Agent 运行治理方法可试

模型路由账单回读清单

升级自动模型选择时，同时记录分类位置、实际模型、延迟、失败回退和账单。

适合你的环节：Claude Code 企业/API/网关升级验收

今天怎么试：在隔离任务中各跑一次正常请求和一次回退路径，读取 /status，并对照费用明细。

边界：只适用于对应 Claude Code 版本与渠道；用户当前版本、账号和计费权限未核验。

采用判断：方法可先写入升级模板；只有实际使用 Claude Code 2.1.278 时执行。

当前做法：当前已知用户使用多种 Agent，但 Claude Code 版本和网关方式未知。

新增收益：补足只看输出质量时遗漏的路由与成本证据。

验证标准：选择结果和账单必须可回读；延迟、质量或费用显著恶化则回退版本或关闭自动模式。

可观测迁移方法可试

可回滚观测迁移法

保留旧输入协议，以兼容层和双轨指标逐段替换采集、sidecar 与聚合组件。

适合你的环节：指标平台、SDK 替换、基础设施迁移

今天怎么试：为一个低风险服务画出旧链路与新链路，在不改应用输入的前提下并行采集一项指标并比较。

边界：Atlassian 的资源收益不可外推；双轨会增加短期成本，需定义误差、丢点和回滚阈值。

边界：属于作者经验方法，未有对照实验；机械拒绝所有措辞建议也可能错过有效编辑。

🧩 本期概念库

1. 长周期任务

一句话解释：需要跨多文件、多工具和多轮验证，完成时间可能以天计的工程任务。

为什么重要：错误会在连续决策中累积，局部正确不能代表最终交付。

团队应用：拆出阶段证据，但最终仍以可构建、可运行和业务回读判定完成。

2. 端到端可交付率

一句话解释：从固定输入到满足全部完成条件的任务比例，而非某一步生成成功率。

为什么重要：它同时暴露工具调用、环境、验证和返工问题。

团队应用：与耗时、人工返工和失败类型一起记录，避免只看补丁接受率。

3. 兼容层迁移

一句话解释：保留旧输入或接口，把替换限制在系统内部的一段。

为什么重要：降低一次性切换的故障半径，并允许双轨比较。

团队应用：为 SDK、指标链或接口迁移预先定义误差与回滚阈值。

4. 责任分工式 AI 写作

一句话解释：人负责事实、判断和最终措辞，模型负责检索、挑错、压缩与机械编辑。

为什么重要：把效率收益与作者责任分开，减少流畅但空洞的代笔。

团队应用：要求每个关键主张有人确认，模型建议逐项接受而非整段复制。

从九成到三成：Agent 为什么一遇到长任务就掉速

同一类 Android 编码 Agent，短任务最高通过率大约九成一，换成长任务后最高只剩约二成八。差的不是一条更聪明的提示词，而是依赖升级、运行时验证、跨文件状态和最终可运行结果。今天值得理解的是：评价 Agent，必须从“补丁像不像”转向“任务有没有真的交付”。

主故事：长度不是唯一难点

Google 发布 Android Bench 2.0 的首批长周期任务。原始短任务最高通过率约九十一%，长任务最高约二十八%。这些任务会涉及依赖升级、新功能、从零构建，甚至跨平台迁移。模型尤其容易在运行时验证、破坏性框架变化和未发布库知识上失败。这里的机制不是“文件多所以更难”这么简单：任务越长，中间决策越多，任何一次错误假设都会污染后续步骤；如果只看代码 diff，不做编译、安装、启动和页面回读，就会把未完成包装成完成。更麻烦的是，长任务的失败往往不是一个明显报错，而是依赖版本选错、页面状态没有真正切换、或者某条异常路径从未走过。它们能在代码审查时显得合理，直到运行环境才暴露。因此评测不能只问模型写了多少代码，还要问它是否在每个阶段保留了可复查状态，失败后能否从最近证据恢复，而不是从头猜测。基准仍是 Google 维护的评测，Agent 配置、任务分布和项目环境都会影响结果，不能直接外推到我们的 App。

快讯一：模型自动选择也有账单边界

Claude Code 2.1.278 把 API、企业和多种网关场景的 Auto mode 默认改为服务端分类器，并提示计费回退。新增价值不只是少一次本地分类，而是让状态页显示当前分类器在哪里运行。升级验收应同时核对模型选择、延迟、失败回退和账单，不要只看最终回答。

快讯二：可观测迁移的收益来自双轨切换

Atlassian 公开了把 StatsD 指标链逐步迁到 OpenTelemetry Collector 的过程：先保持应用端 UDP 接口不变，再合并 sidecar 和聚合层。团队报告昂贵服务平均节约约百分之三点九 CPU，旧聚合器和 Nomad 合计约占指标集群 CPU 请求的百分之三十八。数字是单一团队环境结果，真正可迁移的是先兼容输入，再逐段替换并对照回读。

快讯三：AI 写作的分歧其实是责任分工

两篇本周讨论给出相近边界：让模型做检索、结构诊断和删改建议，但不要把有判断责任的正文外包出去。模型可以指出跳步、重复和反例，却不替作者承担主张。对日报最实用的规则是，证据和判断由人或明确责任主体确定，模型负责压缩与挑错，最终逐句接受。

行动：把移动端验收写进任务契约

今天最值得做的一件事，是给一个真实 Android 或 iOS 任务补齐完成定义：依赖可解析、工程能编译、App 能安装启动、关键页面状态可读、异常路径有证据。然后用同一输入跑现有 Agent，记录完成率、耗时和人工返工。把失败分成环境、知识、工具调用、运行时行为和验收遗漏五类，下一轮只修最主要的一类。这样才能判断该换模型、补工具、改提示词，还是收窄任务。若只生成代码却缺少运行证据，就仍算未完成。

今天的一句话：Agent 的能力上限不由最好看的补丁决定，而由最长的验证链决定。先定义证据，再扩大委派，并保留回退路径。
